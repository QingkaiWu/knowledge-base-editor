# 首次使用示例：把零散工作笔记变成可复用资料

以下是教学构造，展示交互和产出形态，不是实际运行日志。涉及真实资料的研究结论应在阅读、核实后形成，不能直接把本示例当作事实依据。

## 1. 从口语想法开始

用户：

> 使用 $knowledge-base-editor。我想做一个工作笔记知识库，自己记了很多东西，但是需要时总找不到。读者可能也是刚工作的人。

合适的首次回应：

> 你想解决的是“记过却无法复用”。先确认两点：读者最常需要找回的是会议决定、项目经验，还是学习资料？你能提供一份去除隐私的原始笔记，说明后来在哪个场景没能用上它吗？

这一步只补决定范围的缺口，不立即生成整套正文。

## 2. 确认简报

假设后续聊天确认：

- 读者：刚入职的新人，会用文档工具，没有固定整理习惯。
- 读后成果：能把一段会议记录整理成带出处、下一步和检索入口的资料。
- 重点：会议决定与项目经验；暂不讨论个人日记或企业权限体系。
- 材料：作者提供一份脱敏笔记及一次查找失败的具体经历。
- 文风：必要原理讲清楚，操作有例子与验收，避免“建立体系”等无动作建议。

用户确认后，围绕这些目标开展研究。

## 3. 研究后提出大纲

先实际阅读作者材料；需要介绍某个文档工具的具体功能时，再核实该工具的当前官方说明。来源记录写明支持的结论、适用条件和仍缺的证据。

下面仅展示候选大纲的字段与颗粒度，不代表已完成研究：

| ID | 文章 | 读后可完成的事情 | 必要前置 |
| --- | --- | --- | --- |
| A01 | 从一次查找失败，找到记录里缺的内容 | 对照真实查找场景，标出笔记缺失的上下文 | 无 |
| A02 | 把会议记录整理成能跟进的事项 | 写清决定、负责人、时间和来源 | A01 |
| A03 | 用一个项目入口找回相关资料 | 建立入口，并用一次真实查找任务验收 | A02 |

确认大纲与首篇后，再正式写作。

## 4. 一段有操作价值的正文示例

> “后续优化注册流程”不能直接用于跟进：它没有说明谁做、先验证什么、何时回看。先查会议原始记录，补上确实讨论过的信息；没有讨论的字段标“待确认”，不要替参会者做决定。
>
> 把这条记录改成下面四个字段，再交给另一个没有参会的人阅读。对方应能说出下一步是什么、由谁推进、何时检查，以及不确定的信息去哪里核对。如果仍需你口头补充，就把缺的上下文补回记录。

| 字段 | 本例如何填写 |
| --- | --- |
| 下一步 | 验证注册流程中哪一步造成用户困惑；具体方法待确认 |
| 负责人 | 原始记录没有写明，待确认 |
| 检查时间 | 原始记录没有写明，待确认 |
| 来源 | 放入实际会议记录的链接或文件位置 |

这里保留“待确认”比编造负责人和截止时间更有用。

## 5. 继续写下一篇

A02 完成后，A03 可以引用 A02 中的具体整理方法，同时保留建立入口所需的解释。只有实际存在并阅读过的正文才能被引用；未来篇目先登记为计划中。

用户说“继续下一篇”时，先读取项目进度、简报和相关正文，沿用此前反馈，不重新做整轮访谈。
